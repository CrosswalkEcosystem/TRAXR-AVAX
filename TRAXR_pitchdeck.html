Why this exists

Many risk systems still score tokens first. TRAXR-AVAX scores where execution risk actually manifests: on-chain pools. Pool-level analysis captures liquidity depth, concentration, and fee behavior more directly than token-only views, while still requiring a reproducible indexing substrate that downstream scoring can trust.

Common market gap

  • Most systems score tokens, not live pool structure
  • Inconsistent pool identifiers across data consumers
  • Mixed source facts and inferred values with unclear labeling
  • Opaque safety outputs with weak explainability

TRAXR-AVAX response

  • Pool-first, on-chain risk scoring instead of token-first shortcuts
  • Deterministic normalization over snapshot-backed inputs
  • Strict separation of source-backed vs derived fields
  • Decoupled risk scoring with explicit unknown states

What TRAXR-AVAX is, and is not

Is

  • Read-only indexing and normalization layer
  • Transparent pool-level intelligence for AVAX DeFi
  • Input substrate for a separate scoring engine
  • Deterministic behavior prioritizing correctness

Is not

  • Not trading infrastructure
  • Not portfolio tracking
  • Not custody or transaction signing
  • Not a full real-time indexer in alpha

Alpha constraint

Current operation uses local JSON snapshots in data/avaxPools_*.json and manual refresh cycles. This is an interim, versioned ingestion path while the primary target architecture moves to indexing from our own AVAX node.

Layered architecture

Layer 1: Indexed market & protocol data (live, verifiable)

Pool identifiers, token metadata, liquidity, volume, and DEX attribution. Current source is GeckoTerminal snapshots; target source is direct indexing from our own AVAX node.

Layer 2: Derived heuristics (computed, best-effort)

Liquidity depth, volatility impact, and inferred fee metrics where inferable. Always labeled non-authoritative.

Layer 3: Risk & structural signals (decoupled)

Liquidity concentration, fee stability, governance and upgradeability risk handled by the scoring package.

Core pipeline

1. Data ingestion

Versioned snapshot ingestion for AVAX C-Chain pools (currently GeckoTerminal, transitioning toward own-node indexing).

2. Normalization

Deterministic mapping into stable identifiers and field names.

3. External scoring

CTS tiers, dimensional scores, and warnings computed in @crosswalk.pro/traxr-cts-avax.

4. Presentation

Next.js UI and read-only API under /api/traxr/*.

Transparency rules

  • Unknown values are explicit, not hidden
  • Derived metrics are visibly marked heuristic
  • Source-backed values are never overwritten

Scoring model exposed today

Each pool receives a deterministic score (0-100), mapped to CTS tiers (1-6), with explainable dimensions. This pool-first model reflects current cross-chain practice where safety and execution quality are evaluated at liquidity venue level, not token label alone.

Roadmap alignment (repo docs)

Phase 1 (current): indexing & normalization

Versioned GeckoTerminal ingestion today, deterministic snapshots, and normalized AVAX pool metadata while own-node indexing is implemented.

Phase 2: own-node indexing + on-chain resolution

Shift critical indexing paths to our own AVAX node, then expand pool address verification, fee-tier validation, and DEX-specific adapters with explicit RPC fallback.

Phase 3: scoring engine expansion

Enhanced heuristics and confidence modeling in npm scoring package without contaminating raw indexed data.

Phase 4: cross-chain aggregation

Extend normalized model and unify scoring pipeline through per-chain adapters.

How the ecosystem can use TRAXR-AVAX

TRAXR-AVAX is designed as an open, read-only risk signal layer that other products can embed. It helps infrastructure teams expose consistent pool risk context while giving users better decision support.

Wallets

  • Show pool score and CTS tier before swap confirmation
  • Warn users on weaker pools using dimensional flags

DEXes and aggregators

  • Add TRAXR score overlays to pool listings and routing views
  • Let users filter and rank by pool quality, not only APR/volume

Exchanges and listing teams

  • Use normalized pool metrics as an additional diligence input
  • Track structural changes via alerts and trend endpoints

Projects and LP communities

  • Publish pool pages with transparent, evolving score context
  • Share score improvements over time as liquidity quality improves

Regular users

Compare pools side by side, inspect dimension-level metrics, and understand why two pools with the same tokens can have different risk profiles.
